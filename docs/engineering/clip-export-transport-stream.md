# MPEG-TS 片段导出：保留已选关键帧

日期：2026-10-07。基线为 Draft #34 的 `cfd3c5c17a2ff88295688d17fd4aec09b1e5577c`。
本记录只覆盖下列流拷贝边界，不是 Windows 或全部容器的发布验收。

## 可见错误与原因

90 帧、30 fps、GOP30、含 B 帧的 H.264 MPEG-TS 请求 0–89 帧时，旧 writer 报告完成，
实际却从第 30 帧开始，只保留 60 帧。35–49 和 65–79 的短区间则报告没有关键帧。
规划器已正确选择此前的关键帧 0／30／60；错误发生在 writer 的定位阶段。

MPEG-TS 的 FFmpeg 时间戳定位使用 DTS。把已选关键帧的 PTS 传给 backward seek，
仍可能落在该关键帧之后。零起点样本的目标关键包 PTS=0、DTS=-6000，定位到 PTS=0
后最先返回的却是非关键包 PTS=3000、DTS=0。随后等待关键包就会遗漏当前 GOP。
这不是可推广到其他容器的固定时间偏移；参见
[FFmpeg MPEG-TS 的 read_timestamp 实现](https://ffmpeg.org/doxygen/7.1/mpegts_8c_source.html#l03346)。

## 最小修复

- 仅对 FFmpeg 识别为 `mpegts` 的输入跳过该次时间戳 seek，沿输入压缩包顺序定位
- 首包必须是关键包，且相对源原点归一化后的最近微秒时间，严格等于计划的关键帧时间
- 使用与 `keyframeTimes()` 相同的转换，不把微秒再转回 ticks 后猜测边界，也不把缺失的
  关键帧替换成下一个 GOP；找不到时失败，原目标文件保留
- 选中后继续原有流拷贝、出点参考包、取消和原子发布路径；MP4／Matroska 定位未改

产品语义仍是「向前一个关键帧对齐」：35–49 导出从 30 开始，不能承诺从 35 精确成帧。
65–79 样本保留 21 帧，其中结尾参考帧仍遵循原有 B 帧说明。没有重编码或新增 UI。

## 成本与未验收边界

MPEG-TS 原有无索引关键帧查询已扫描全文件；本修复又顺序读取到已选关键帧，再复制区间。
这是按压缩包数量线性增长的定位，逐包检查取消，不解码、不缓存整个前缀、不阻塞 GUI。
128×96 小样本的约 5／10 分钟输入分别为 7.2／14.4 MB，关键帧查询各读 9003／18003 次，
末尾导出同样各读 9003／18003 次；查询约 13／26 ms，复制调用约 14／24 ms。
这些暖缓存小文件数值只证明本次读量没有变成逐 GOP 重扫，不代表高码率或慢磁盘性能。
较晚区间的定位成本确实增加，不能声称导出性能门禁已通过。

未知原点的旧回退路径会先扫描再以 PTS rewind；若因此丢失计划的关键帧，严格匹配会失败，
本轮不重写该路径。时间戳回绕／不连续、重复关键帧时间、粗容器时钟和缺失包位置等边界
也未普遍验收，不据这些案例声称所有 TS 或全部容器均可用。
