# CI 与发布效率

2026-10-25 整理。当前软件CI已迁至GitHub托管Windows，旧“单台自托管排队”分析不再作为
增加机器或每次推送全量重配的理由。运行位置见[托管CI](hosted-windows-ci.md)，
本地范围见[构建选择表](../building.md#开发循环与完整验收)。

## 当前做法

- 本地按影响范围迭代，成功检查不在相同输入上重复；不例行`-Fresh`或清空依赖。
- 普通软件作业使用托管runner，硬件作业仅手动触发；发布只接受对应候选的适用证据。
  具体路由由workflow与其契约检查维护，不在此复制测试数量。
- 构建/脚本/公共注册变化覆盖受影响preset；不能只在一种配置上验证就推断core/ui-dev皆正常。
  也不要求文案或文档改动先配置所有preset。
- 发布前核对候选SHA和相关CI；发布中同时关注质量、构建、证据核验与打包作业。
  重跑失败范围前先定位原因，旧候选的绿灯不认证新候选。
- ZIP按[打包政策](../building.md#zip-只打包必要运行时)读回、验哈希、检查载荷并比较上一版文件清单。
  对渲染/剪贴板环境缺失的跳过要明确说明，不能把跳过当通过，也不能吞真实断言。

## 可独立评估的自动化

旧评审提出的双通道发布监控、草稿包下载/验收整合，以及上传失败后复用已验证artifact，
仍可按实际发布摩擦选择。实施前先核对现有workflow是否已覆盖；这些建议不成为每次开发的前置任务。
若拆分构建与发布，必须保留同SHA/同产物身份、读回校验和全部发布门禁，不能重试到另一份旧ZIP。

不默认扩大超时、增加自托管机器或清理远程分支；这些动作分别需要测量依据与相应任务授权。
历史v2.3.0耗时/故障记录可从本文件Git历史读取。
