# 12｜可复现实验、最小用例与验收脚本设计

## 核心结论

每个整改项都必须从“用户感觉”转成可重复实验。实验记录必须固定代码、媒体、硬件、输入节奏和判定规则；不能只录一段视频说“看起来顺了”。本文件给出当前已确认问题与高概率风险的最小实验设计，以及目标方案完成后的验收预期。

### 必需原则

- 保存原始样本；
- 实验前写 expected 与判定；
- 不删除失败 run。

## 三、EXP-C01｜Reference 与 Timeline Master 分离

### 当前行为证明

**目标命题**

```text
在旧模型中，将 Reference 从源 0 改为源 1 会使 canonical descriptor/timeline
随新 Reference 改变。
```

### 最小 fixture

- A：30 fps，300 帧，10 秒；
- B：24 fps，240 帧，10 秒；
- 两路均可打开；
- 当前显示 A canonical frame 150（5 秒）。

### 步骤

1. Open A/B，A 为 Reference；
2. 等待 Ready，seek A frame 150；
3. 记录 canonical rate/count、media time、displayed frame；
4. Change Reference to B；
5. 等待 transaction；
6. 记录新 canonical rate/count/frame/time；
7. 导出 trace。

### 当前预期

旧实现中 canonical source 随 Reference 变化。该实验用于证明 C-01，不作为失败。

### V2 验收

1. `SetReference(B)`：
   - TimelineMaster 仍 A；
   - canonical rate/count/frame 不变；
   - Pair/label 可变；
   - provider 不因时间线改变重建。
2. `SetTimelineMaster(B)`：
   - 显式产生 timeline revision；
   - 位置按 5 秒映射到 B；
   - 返回 RestoreAccuracy；
   - Range/markers 通过 MediaTime remap；
   - 失败保留 A master。

### 自动测试

```text
ComparisonWorkflowTests.SetReferenceDoesNotChangeTimeline
SessionTopologyTests.TimelineMasterAndReferenceAreIndependent
MainQmlComparisonIdentityTests.ReferenceAndTimelineBadgesAreDistinct
```

## 四、EXP-C02｜Pair Ordinal 跨拓扑泄漏

### 历史问题复现

Fixture：A/B/C，不同纯色，settings 预置 `differenceEdge = Between0And2`。

### 步骤

1. 以三路打开，选择 A/C Difference；
2. 关闭应用保留 Preferences；
3. 仅打开 A/B；
4. 切换 Wipe 与 Diff；
5. 截取画面、记录 effective pair；
6. 再加入 C；
7. 观察 Pair 是否静默恢复 A/C。

### 旧实现/历史风险

当前版本会 normalize 两路为 0-1，但保留 preference，第三路回来后 0-2 可能恢复。历史版本曾造成黑屏。

### V2 验收

- global settings 不保存具体 session pair；
- 两路选择产生 SourceKey(A,B)；
- 加 C 后 Pair 仍 A/B，除非用户选择；
- reorder 后仍 A/B；
- remove A 后 deterministic fallback；
- migrate old setting 时只转换为 default policy；
- pixel capture 与 UI label 一致。

### 测试

```text
ComparisonSemanticsMigrationTests.LegacyEdgeDoesNotBecomeSessionIdentity
ComparisonWorkflowTests.ReorderKeepsPairBySourceKey
HardwarePairSwitchTests.TwoToThreeSourcesKeepsExplicitPair
```

## 五、EXP-C03｜连续后退 Exact Seek 风暴

### 目标命题

```text
当前 delta=-1 不进入 interactive sequential stream，
每次重复会触发 Exact navigation；在输入快于 seek 完成时产生高 cancel/generation/seek。
```

### Fixture

F01、F03、F08；从中间安全帧开始。

### 输入

- 30 Hz，300 个 `StepFrames(-1)`；
- 另做饱和模式：只要 lookahead 接受就提交；
- forward 作为对照。

### 记录

```text
presented frame sequence
command outcomes
generation delta
exact seek delta
sequential request count
cancel count
decoder reopen
p50/p95/p99
frame budget
```

### 当前判定

若 reverse exact seek/generation/cancel 显著高于 forward，且有节奏断裂，即证明机制不对称。即使肉眼尚可，路径差异仍是 C。

### Reverse Window 验收

- 300 个 accepted 命令严格呈现 300 个 `-1`；
- sequence error 0；
- current/prepared FrameSet 完整；
- 窗口 warm 后 exact seek delta ≤ 预定小值；
- window hit ratio 达到基线目标；
- decoder reopen 0；
- 4K/P010 内存不超预算；
- 取消后无 release tail。

## 六、EXP-C04/H-01｜Range Loop 越界与边界停顿

### Deterministic Fake Test

建立 canonical frames 0～99、60 fps，Range `[20, 25]`。Fake clock 可一次推进：

- 16 ms；
- 100 ms；
- 500 ms；
- 2500 ms。

Renderer ACK 可延迟/乱序。

### 旧 QML 模式验证

在集成测试中让播放 catch-up 计算到 26/30，再由 QML 收到 displayedFrame 后发 seek。若画面先提交 >25，则 H-01 被确认。

### Native Range 验收

对所有 clock jump：

```text
presented frames ⊆ [20,25]
25 is presented and ACKed
loop next visible frame = 20
no partial set
```

事件排列：

- device loss at 25 publish；
- late ACK 25；
- pause at 25；
- clear range before ACK；
- source alignment revision；
- In=Out；
- VFR。

### 性能

`loop_boundary_p95` 记录 25→20 间隔；不以跳过 Out 换低延迟。

## 八、EXP-C06/H-02｜高频投影与 QML 重算

### 命题

```text
单一 ReviewController stateChanged 可能让高频 frame update
触发低频 source/alignment/error QVariant 与字符串重算。
```

### 测量方法

1. 1080p120 单源/三源；
2. Qt/QML profiler；
3. 在 `ReviewController` 每个 projection getter/model build 增计数；
4. 播放 60 秒；
5. 记录 stateChanged、getter、allocation、binding evaluation；
6. ViewModel Split 后同样运行。

### 判定

H-02 只有在 profiler 显示非必要低频计算与帧率相关时确认。若没有，则架构拆分仍可为可维护性服务，但不能宣称性能收益。

### 目标

- frame update 只触发 Playback/Timeline 高频属性；
- source/compatibility/pair list build 不随帧数增长；
- GUI CPU/alloc 有实测改善或至少无退化；
- QML frame pacing 不变差。

## 十八、实验完成定义

一个问题只有在以下条件同时满足时才可标记“已解决”：

1. 原始最小复现能在旧基线稳定失败；
2. 根因由 trace/code/test 指向同一机制；
3. 新实现让同一实验通过；
4. 至少一个对抗用例通过；
5. 相关历史回归通过；
6. 正确性、性能、资源均未退化；
7. exact commit 与环境有记录；
8. 独立 reviewer 能从 artifact 重现结论。

这套实验体系确保后续任何争议都能回到“哪个帧、哪个身份、哪个事件、哪个像素、哪条指标”，而不是停留在主观描述。
