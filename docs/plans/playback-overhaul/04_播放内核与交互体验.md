# 04｜播放内核与交互体验设计

## 核心结论

Toy 的播放内核不需要替换；真正需要整改的是**把不同导航工作负载从一个泛化的 Seek/Play 路径中分离出来**。随机定位、连续前进、连续后退、实时播放、时间轴 Scrub、范围循环，对缓存、取消、时钟和“是否允许跳帧”的要求完全不同。继续让它们共享隐式规则，会导致某一类体验优化破坏另一类正确性。

推荐新增 `NavigationWorkflow` 与 `PlaybackWorkflow` 两个内部工作流，并明确六种执行策略：

| 工作负载 | 用户语义 | 解码策略 | 是否允许跳过 canonical 帧 | 终止方式 |
|---|---|---|---|---|
| Exact Seek | 只关心目标帧 | keyframe seek + decode-to-target | 中间帧不呈现 | 新目标 latest-wins |
| Forward Step | 每一帧都要看到 | 顺序游标 + read-ahead | 不允许 | 输入耗尽或被新导航取代 |
| Reverse Step | 每一帧都要看到 | GOP 窗口反向消费 | 不允许 | 输入耗尽或窗口失效 |
| Realtime Play | 尽量跟随媒体时钟 | 顺序管线 + cadence | 由显式策略决定 | Pause/End/Range |
| Scrub Preview | 快速反馈位置 | 低成本 latest-wins 预览 | 只呈现最新预览 | Commit/Cancel |
| Range Loop | 严格停留在闭区间 | 内核原生边界与重锚定 | 由播放策略决定，但不可越界 | Stop/Clear/Topology change |

这套拆分的目标不是增加状态机数量，而是让每个状态机拥有可审查的契约，同时继续由单一协调器串行提交媒体真相。

## 一、显式播放策略：消除隐藏的“保帧/追时钟”混合语义

### 1.1 当前风险

当前播放实现保留短时阻塞内的每个完整 `FrameSet`，超过容忍窗口后按 wall-clock 追赶。这一策略对评审工具有价值，但它是隐藏在常量和调度逻辑中的混合模式：

```text
短暂落后：逐帧补齐
持续落后：跳到当前媒体时间
```

用户无法知道自己是在“审查每一帧”还是“实时播放”。如果 GPU、解码器或窗口合成发生 1～2 秒抖动，播放可能先慢放补帧，再突然追赶；技术上完整、体验上却不稳定。

### 1.2 目标 API

新增纯领域类型：

```cpp
enum class PlaybackContinuityPolicy : std::uint8_t {
    ReviewEveryFrame,   // 不主动跳 canonical 帧；允许相对真实时间变慢
    RealTime,           // 追随媒体时钟；只跳完整 FrameSet
    Contextual,         // 单源默认 RealTime，多源评审默认 ReviewEveryFrame
};

struct PlaybackSettings final {
    PlaybackContinuityPolicy continuity = PlaybackContinuityPolicy::Contextual;
    RationalRate speed{1, 1};
};
```

`Contextual` 只在设置解析阶段转换成确定值，运行中的 `PlaybackRun` 必须保存解析后的策略，不允许每帧读取 UI/Preferences 再改变语义。

### 1.3 两种模式的严格契约

**ReviewEveryFrame**

- canonical 帧号必须单调连续；
- 不因 wall-clock 落后跳帧；
- 呈现速度可以低于源帧率；
- UI 状态栏显示“Frame-accurate playback · running slow”；
- 健康门禁是完整性和延迟上界，而不是实时性。

**RealTime**

- 允许根据 canonical timeline 计算目标帧；
- 只允许跳过完整的 canonical `FrameSet`，不能单路跳；
- 必须统计 `droppedCanonicalFrameSets`、最长连续跳过、原因和时间段；
- 追赶前不得回退帧号；
- UI 状态栏显示“Real-time · dropped N frame sets”，且该状态可展开查看。

### 1.4 切换策略

播放中切换策略不应修改当前 `PlaybackRun` 的时钟规则。推荐：

1. 设置写入 Preferences；
2. 当前播放继续到下一安全边界；
3. 内核发出 `PlaybackPolicyChangePending`；
4. Pause 后重新 Play，或在当前 ACK 完成后显式重建 run；
5. 新 run 使用新策略和新 `playbackRevision`。

这样避免在一帧等待 ACK 时突然改变 catch-up 算法。

## 二、统一导航状态机，而不是继续扩展 `beginStep()`

### 2.1 建议的数据模型

```cpp
enum class NavigationKind : std::uint8_t {
    Exact,
    ForwardStep,
    ReverseStep,
    ScrubPreview,
};

struct NavigationScope final {
    SessionIdentity session;
    TopologyRevision topologyRevision;
    TimelineRevision timelineRevision;
    AlignmentRevision alignmentRevision;
    PlaybackGeneration generation;
    NavigationRunId runId;
};

struct PendingPresentedFrame final {
    FrameRequestContext context;
    FrameId target;
    std::optional<FrameSet> frameSet;
    bool providerSucceeded = false;
    bool published = false;
    bool presented = false;
    std::optional<TimerId> deadline;
};
```

所有工作负载可以复用 `PendingPresentedFrame` 的三方完成条件：

```text
FrameSetReady + RequestSucceeded + PresentationACK
```

但不能复用输入队列、时钟或允许跳帧的规则。

### 2.2 命令终态

每一个外部命令必须恰好得到一个终态：

```cpp
enum class CommandOutcome {
    Succeeded,
    Busy,
    Canceled,
    Failed,
    Closed,
};
```

进一步规定：

- `Busy`：命令未被接纳，用户可重试；
- `Canceled`：已接纳但被新合法意图取代，不设置 `lastError`；
- `Failed`：媒体、渲染、超时、数据不一致等真实错误；
- `Closed`：有序关闭；
- 已收到 Presentation ACK、但 provider terminal 尚未到达时，命令所有权仍不得丢失；
- 任何 teardown 都必须遍历 current/prepared/queued 三层所有者。

## 三、双向逐帧：补齐当前最明显的不对称

### 3.1 前进逐帧保留现有快路径

现有 `Interactive Forward Step Stream` 的关键思想正确：

- 一个 run 内只递增一次 generation；
- 使用 `Sequential` request；
- 保留 decoder/demux cursor；
- 1 current + 1 prepared；
- decoder 内部有限 read-ahead；
- 输入目标只允许有限领先；
- 每一帧仍等待完整 FrameSet 与 ACK；
- 随机导航会取消 run，而不是把错误写入 `lastError`。

整改时不要把它重新并回普通 `PlaybackRun`。应该提取公共帧提交组件，并把名称泛化为 `DirectionalStepRun`，但前进与后退仍有不同媒体策略。

### 3.2 后退不能假装成“反向解码”

H.264/HEVC 等长 GOP 编码通常不支持廉价逐帧逆向解码。成熟播放器的反向体验通常来自“从前一个关键帧正向解码一段，再反向消费已解码帧”。因此目标不是让 FFmpeg 倒着解码，而是建立有界 **Reverse GOP Window**。

```cpp
struct ReverseWindow final {
    SourceKey source;
    FrameId inclusiveStart;
    FrameId inclusiveEnd;
    std::deque<DecodedFrame> framesInDisplayOrder;
    std::size_t bytes = 0;
    DecoderRevision decoderRevision;
};

struct ReverseStepRun final {
    NavigationScope scope;
    FrameId lastQueuedTarget;
    std::deque<CommandContext> queuedCommands;
    std::optional<PendingPresentedFrame> current;
    std::optional<PendingPresentedFrame> prepared;
    std::vector<ReverseWindow> sourceWindows;
};
```

### 3.3 单源反向算法

以当前显示帧 `N` 为例：

1. 查询 Presentation Index，定位包含 `N-1` 的前一个随机访问点；
2. 从 keyframe/seek point 正向解码到 `N-1`；
3. 只保留目标窗口内的 display-order 帧；
4. 将 `N-1, N-2, ...` 反向送入 FrameSet 组装；
5. 当用户继续后退且窗口尚有帧时零 seek 消费；
6. 窗口耗尽时异步建立前一个窗口；
7. current + prepared 仍只向渲染器推进两个完整 FrameSet；
8. 新的随机 seek/play/拓扑变化立即取消窗口构建。

### 3.4 多源反向算法

多源会话不能为每路独立决定 canonical 目标。流程必须是：

```text
canonical N-1
    ↓ alignment mapping
source frame A / B / C
    ↓ each source window lookup/decode
complete FrameSet assembly
    ↓ render + ACK
commit canonical N-1
```

如果某一路映射为 missing，则用明确的 `MissingFrameResource`/缺失状态参与完整 FrameSet，而不是等待不存在的帧。

### 3.5 内存与窗口策略

反向窗口必须受共享 `FrameBudget` 约束，不能通过“缓存整段 GOP”无条件换流畅度。

推荐起点：

- 单源窗口目标：最多 24～48 个 1080p NV12 帧，具体由字节预算决定；
- 多源按权重公平分配；
- 4K/P010 自动缩短窗口；
- 当前正在呈现与 prepared 帧不可被驱逐；
- 构建新窗口前先申请预算，失败则退化为单次 Exact Seek；
- 记录 `reverse_window_hit_ratio`、`reverse_window_build_p95`、`reverse_exact_fallback_count`；
- 不以固定“帧数”作为唯一上限，必须同时有 bytes 与 time-span 上限。

### 3.6 后退逐帧验收

- 长按 Left/A 呈现严格的 `N-1, N-2, ...`，无中间帧缺失；
- 每个已接纳命令恰好一个终态；
- 健康长按期间 decoder reopen 为 0；
- 窗口切换不出现 A/B/C 不同帧；
- 取消后无陈旧 ACK 提交；
- 在 4K/P010 预算不足时允许变慢，但不能 OOM 或破坏原子性。

## 四、随机 Seek 与多帧 Jump：latest-wins 但必须可解释

### 4.1 Exact Seek 适用范围

以下操作继续使用 Exact：

- 点击某个离散时间点；
- Home/End；
- ±5 帧、±1 秒、±30 秒；
- 更换 canonical timeline master 后的位置恢复；
- 对齐 revision 改变；
- Scrub Commit；
- 外部命令行定位。

### 4.2 合并规则

连续 Exact Seek 应使用 latest-wins，但必须区分：

- **尚未入队**：直接 Busy；
- **已入队未开始**：旧命令 Canceled；
- **正在解码**：请求取消，旧命令最终 Canceled；
- **已发布等待 ACK**：不能复用 buffer；生成新 generation，旧 ACK 只用于资源退休，不得提交；
- **已 ACK**：目标已经可见，命令 Succeeded，随后再执行新 seek。

### 4.3 位置恢复

Source topology 或 timeline master 变化时，默认按 `MediaTime` 恢复，而不是复用同一 frame number：

```cpp
struct PositionBookmark final {
    MediaTime mediaTime;
    std::optional<FrameId> priorCanonicalFrame;
    SourceKey priorTimelineMaster;
};
```

恢复结果必须返回：

```cpp
enum class RestoreAccuracy {
    ExactMediaTime,
    NearestFrameAtOrBefore,
    ClampedToStart,
    ClampedToEnd,
};
```

UI 可以显示一次非阻塞提示，避免用户误以为“Frame 100”在不同 canonical source 中仍是同一时刻。

## 五、内核原生 Range Loop

### 5.1 为什么必须从 QML 移走

范围循环属于媒体时钟和 canonical timeline 规则。由 QML 在 `currentFrame >= outFrame` 后发 `seek(in)`，至少存在三类结构性风险：

- RealTime catch-up 可能直接计算到 Out 之后；
- UI 事件投影与 ACK 有延迟，边界处理依赖信号时序；
- 切换 source/reference/alignment 后范围 remap 与播放 run 分离。

这不意味着当前一定会越界，但它无法从内核契约证明“永不越界”。

### 5.2 命令与状态

```cpp
struct PlaybackRange final {
    FrameId inInclusive;
    FrameId outInclusive;

    [[nodiscard]] bool isValid() const noexcept {
        return inInclusive.isValid() &&
               outInclusive.isValid() &&
               inInclusive.value() <= outInclusive.value();
    }
};

struct SetPlaybackRangeCommand final {
    CommandContext context;
    std::optional<PlaybackRange> range;
    bool loop = false;
};

struct PlaybackRun final {
    ...
    std::optional<PlaybackRange> range;
    bool loop = false;
    std::uint64_t completedLoops = 0;
};
```

`SessionSnapshot` 暴露：

- range；
- loop active；
- next boundary；
- completed loops；
- range remap status；
- 是否因 topology/timeline change 被清除。

### 5.3 边界状态机

闭区间 `[In, Out]` 的规则：

1. Play 从范围外启动：先 Exact Seek 到 In，ACK 后开始；
2. 当前目标不得计算到 `Out + 1`；
3. `Out` 必须完整呈现并 ACK；
4. 非 Loop：提交 Out 后进入 Paused；
5. Loop：提交 Out 后重锚到 In；
6. 可以保留/预取 In 的帧资源，但不得在 Out ACK 前可见；
7. VFR 使用 canonical timeline time，不以固定 fps 推算；
8. 用户在 loop 中手动 seek 到范围外：默认停止 loop，并保留 range 标记；
9. 清除 range 不打断当前已发布帧，下一边界开始采用普通播放；
10. topology/timeline change 通过 MediaTime remap，失败则清除并说明原因。

### 5.4 单帧范围

`In == Out` 的语义应明确：

- 点击“播放范围”时只确保该帧可见；
- 不启动高速 seek loop；
- `completedLoops` 不递增；
- UI 显示“Single-frame range”。

## 六、Scrub 会话：拖动时快速、松手后精确

### 6.1 不应采用的方案

禁止把 `MouseArea.onPositionChanged` 的每个事件直接转换成普通 `SeekFrameCommand`。这会造成：

- exact queue 取消风暴；
- generation 高频变化；
- decoder interrupt/reopen；
- QML 输入频率决定媒体负载；
- 长视频/GOP 下出现越来越长的尾部工作。

### 6.2 目标交互

```cpp
struct BeginScrubCommand   { CommandContext context; };
struct UpdateScrubCommand  { CommandContext context; MediaTime target; };
struct CommitScrubCommand  { CommandContext context; MediaTime target; };
struct CancelScrubCommand  { CommandContext context; };
```

`ScrubSession` 规则：

- Begin 自动 Pause，但保留原先是否 playing；
- Update latest-wins，最大提交频率由内核节流，例如 15～30 Hz；
- 优先返回缩略图/代理预览，不修改 authoritative `displayedFrame`；
- 预览状态单独暴露 `previewFrame/previewTime/previewImage/revision`；
- Commit 发起一次 Exact Seek，ACK 后清除 preview；
- Cancel 清除 preview，恢复原 displayedFrame；
- Commit 后可按用户设置决定是否恢复播放；
- 拖出窗口、Esc、失焦、设备丢失都有确定性取消语义。

### 6.3 预览质量阶梯

根据压力选择：

1. 已缓存缩略图；
2. 低分辨率独立 decoder；
3. 当前主 decoder 的低优先级 Exact preview；
4. 仅显示时间码/帧号占位；
5. 最终 Commit 永远走主精确路径。

任何预览都必须带 `PreviewQuality`：

```cpp
enum class PreviewQuality {
    CachedThumbnail,
    ProxyDecoded,
    FullResolutionDecoded,
    MetadataOnly,
};
```

UI 不应把 MetadataOnly 占位当成已经解码的画面。

## 七、独立缩略图服务

### 7.1 当前模型的限制

从已呈现画布 `grabToImage()` 只能缓存用户已经看过的帧，并且捕获的是当前合成视图，不是任意时间点的稳定源预览。它适合轻量缓存，但不能承担专业长视频导航。

### 7.2 端口设计

```cpp
struct ThumbnailRequest final {
    RequestContext request;
    SourceKey source;
    TimelineRevision timelineRevision;
    FrameId canonicalFrame;
    PixelExtent targetExtent;
    ThumbnailColorPipelineVersion colorVersion;
    ThumbnailIntent intent; // Hover, Scrub, Lane
};

class IThumbnailProvider {
public:
    virtual PortSubmitResult submit(
        ThumbnailRequest,
        std::shared_ptr<IThumbnailEventSink>) = 0;
    virtual void cancel(const RequestContext&) noexcept = 0;
};
```

缓存键：

```text
source fingerprint
+ source frame after mapping
+ timeline/alignment revision
+ target dimensions
+ color pipeline version
+ rotation/SAR presentation version
```

不能只用 canonical frame 号，否则更换 Reference/Pair 后会拿到错误图片。

### 7.3 调度策略

- hover：latest-wins；
- scrub：高于 lane 预热，低于主导航；
- thumbnail lane：空闲时填充；
- 主播放/步进压力高时暂停；
- 单独的低优先级 decoder，不夺取主 decoder cursor；
- 结果在后台缩放成目标尺寸后再进入 GUI；
- LRU 同时按条目数与字节数限制；
- 取消或 session revision 改变后，结果只可用于资源释放，不能投影。

### 7.4 多源预览

默认展示 Timeline Master 或 Reference。用户可以选择：

- Reference only；
- Active Pair split thumbnail；
- Difference thumbnail；
- Focused source。

组合缩略图的缓存键必须包含 `PairKey` 和 compare pipeline revision。

## 八、时间轴与导航 UX

### 8.1 显式缩放控件

保留 Ctrl+滚轮，但增加可发现控件：

```text
[−] [1.0×] [+] [Fit] [Follow playhead]
```

时间轴模型直接接收 `currentFrame`，不要用 `progress * totalFrames` 反推，避免大帧数与 VFR 场景中的舍入漂移。

### 8.2 键盘行为

时间轴获得焦点时：

- Left/Right：移动预览游标 1 帧；
- Shift+Left/Right：5 帧；
- Ctrl+Left/Right：1 秒；
- Home/End：可见窗口首尾；
- Ctrl+Home/End：全片首尾；
- Enter：Commit；
- Esc：Cancel；
- `+/-/0`：放大/缩小/Fit；
- PageUp/PageDown：平移一个可见窗口。

这些键只在时间轴焦点上下文生效，不能与全局媒体快捷键重复触发。

### 8.3 Marker 密度

大量 anomaly/anchor/missing marker 不应直接创建数千个 QML Rectangle。目标模型应按当前窗口聚合：

```cpp
struct TimelineBucket final {
    FrameRange range;
    std::uint32_t missingCount;
    std::uint32_t duplicateCount;
    std::uint32_t anomalyCount;
    std::optional<float> worstScore;
};
```

缩放到足够细时再展开单帧 marker。聚合必须确定性，tooltip 显示“此区间 37 个异常”，而不是静默截断到固定 256 个。

## 九、播放速度与音频扩展边界

### 9.1 无音频阶段

可先支持视觉播放速度：

- 0.25×、0.5×、1×、1.5×、2×、4×（实现：`PlayCommand.speed` / `SetPlaybackRateCommand`，cadence 以 `due(n) = wallAnchor + (timeline(n) - timeline(anchor)) / speed` 缩放，速率切换时以当前显示帧重新锚定）；
- `ReviewEveryFrame` 在低速下延长 cadence；
- `RealTime` 在高速下仍按 canonical timeline 选择完整 FrameSet；
- 步进不受播放速度影响；
- Diff/analysis 与 source 同速。

### 9.2 引入音频后的时钟

音频不应直接塞入现有 coordinator。建议新增：

```cpp
class IPlaybackClock {
public:
    virtual MediaTime now() const noexcept = 0;
    virtual void start(MediaTime anchor, RationalRate speed) = 0;
    virtual void pause() = 0;
    virtual void seek(MediaTime) = 0;
};
```

策略：

- 有音频、1×/常用速度：音频设备时钟为 master；
- 无音频：steady clock 为 master；
- ReviewEveryFrame：视频提交为 master，音频默认静音或显式 time-stretch；
- 多源只播放一条明确选择的音轨；
- 切换音轨不改变 Timeline Master；
- 音频失败不得破坏视觉 FrameSet 提交，可降级静音并报告。

## 十、观测指标与性能门禁

新增统一 `PlaybackTelemetrySnapshot`：


## 十一、推荐实施顺序

1. 先把当前 playback 与 navigation 事件转成可重放 trace，并补齐命令终态审计；
2. 抽取公共 `PendingPresentedFrame`，不改变行为；
3. 引入显式 `PlaybackContinuityPolicy`，先复刻现有 Contextual 行为；
4. 把 Range Loop 移到 Application，删除 QML 媒体循环状态机；
5. 实现 Reverse GOP Window，并建立 held-backward 硬件门禁；
6. 实现 ScrubSession 与独立 ThumbnailProvider；
7. 最后加入播放速度，音频作为独立里程碑。

最关键的边界是：**任何流畅性优化都不能绕过完整 FrameSet 与 Presentation ACK；任何正确性策略也不能无限堆积工作或隐藏播放模式。**
