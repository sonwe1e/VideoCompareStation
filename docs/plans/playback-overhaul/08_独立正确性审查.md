# 08｜独立正确性审查与多角色执行协议

## 核心结论

这个项目的高风险不是单个函数写错，而是一个局部修复在另一个异步边界制造新回归。因此实施阶段必须由**职责隔离的六个角色**分别产出证据，而不是同一实现者写完代码后自行勾选清单。

六个必需角色：

```text
A. Architecture
B. Root-cause Investigation
C. Implementation
D. Independent Correctness Review
E. Regression / Edge-case Review
F. Final Verification
```

角色结论冲突时禁止投票。唯一裁决流程是：

```text
缩小争议命题
→ 指明可观测结果
→ 构造最小可复现实验
→ 固定 commit/toolchain/fixture
→ 采集 trace/test/pixel/perf 证据
→ 由证据更新设计或实现
```

没有证据时，结论保持“未确定”，不得以资历、人数或措辞强度决定。

## 一、执行组织

### 1.1 每个工作包的独立交付物

```text
work/<id>/
  00_problem_statement.md
  01_architecture_review.md
  02_root_cause_report.md
  03_implementation_plan.md
  04_patch_manifest.md
  05_correctness_review.md
  06_regression_review.md
  07_final_verification.md
  evidence/
    tested-commit.txt
    environment.json
    test-results/
    traces/
    screenshots/
    pixel-captures/
    performance/
```

每份报告必须写明：

- 审查 commit；
- 工具链/平台；
- 输入 fixture；
- 已验证事实；
- 推断；
- 未验证内容；
- 阻断项；
- 证据路径。

### 1.2 独立性要求

- Architecture 角色不直接修改实现；
- Root-cause 角色先于 Implementation 看到最终方案，但不以实现便利修改问题定义；
- Correctness reviewer 不使用实现者的解释作为唯一证据，必须从 diff、契约、测试和 trace 独立重建行为；
- Regression reviewer 从“如何破坏它”出发，不复述 happy path；
- Final verifier 只测试待发布精确 SHA；
- 同一人可在资源有限时承担多个角色，但不能在同一轮同时作为 Implementation 和唯一 Correctness approver；报告必须分开完成并显式标注角色切换。

## 二、A｜Architecture 角色

### 2.1 任务

判断改动是否落在正确边界，以及是否破坏现有不变量。

必须回答：

1. 状态的唯一 owner 是谁；
2. 命令从哪里进入、由谁串行化；
3. 异步结果携带哪些身份；
4. 哪个 revision 变化会使结果陈旧；
5. 是否增加了新的 event loop/媒体真相；
6. Domain/Application 是否泄漏 adapter 类型；
7. 是否保留完整 FrameSet 与 ACK；
8. 缓存/队列是否有界；
9. 失败能否保留旧 Ready Session；
10. UI 是否只表达意图。

### 2.2 输入

- 目标问题；
- 当前架构文档；
- 相关源码和 CMake 依赖；
- 现有不变量；
- 历史回归；
- 候选方案。

### 2.3 输出模板

```text
Decision: Accept / Revise / Reject
Scope boundary:
State owner:
Command path:
Async identities:
Failure boundary:
Resource budget:
Migration path:
Rejected alternatives:
Open questions:
Required architecture tests:
```

### 2.4 阻断条件

以下任一出现即阻断：

- 每路独立播放器自行更新 UI；
- QML/GUI timer 成为媒体时钟；
- 新 worker 直接写 `SessionSnapshot`；
- renderer 读取 UI model；
- async result 缺少 topology/timeline/alignment/device revision；
- 新缓存无字节上限；
- 失败前先销毁旧 Ready Session；
- 为便于实现绕过 Presentation ACK；
- 全局 Preferences 保存会话 SourceId/slot；
- 新功能要求 Application 依赖 FFmpeg/Qt/D3D11 类型。

## 三、B｜Root-cause Investigation 角色

### 3.1 任务

把用户现象还原成可验证的事件链，不以“看起来像”代替根因。

### 3.2 调查方法

1. **最小化输入**：从真实大视频缩小到能复现的最小 codec/GOP/分辨率；
2. **固定环境**：commit、GPU、driver、refresh rate、DPI、decode backend；
3. **建立时序**：Command → Provider → Decode → FrameSet → Render → ACK → Snapshot；
4. **比较正常/异常 trace**；
5. **故障注入**：延迟、Busy、cancel、device loss、缺帧；
6. **源代码反证**：检查所有分支，不只找支持假设的代码；
7. **构造单元/组件测试**；
8. **确定必要与充分条件**。

### 3.3 根因报告格式

```text
User-visible symptom:
Reproduction rate:
Minimal fixture:
Trigger:
Necessary preconditions:
Observed event sequence:
Expected event sequence:
First invariant violation:
Root cause:
Contributing factors:
Non-causes ruled out:
Confidence:
Reproduction/test artifact:
```

### 3.4 “根因”判定标准

不能把下列内容直接称为根因：

- “代码太复杂”；
- “可能是线程问题”；
- “缓存不够”；
- “Qt 有 Bug”；
- “FFmpeg 慢”；
- “GPU driver 不稳定”。

合格根因必须精确到可改变的机制，例如：

```text
连续 -1 输入每次进入 beginSeek，导致 generation++、
active Exact decode 被 cancel，并使顺序 cursor/read-ahead 失效；
因此按键频率高于单次 seek 完成率时产生可重复的可见顿挫。
```

### 3.5 冲突示例

假设 Architecture 认为“需要 Reverse GOP Window”，Implementation 认为“把 cache 从 12 MiB 提到 128 MiB 即可”。

裁决实验：

- 固定缓存 12/32/128 MiB；
- 同一长 GOP fixture；
- 记录 exact seek、decoder reopen、连续呈现、P95；
- 若大缓存仍存在每次 generation/cancel，则缓存不是根修复；
- 若 Reverse Window 在预算受限下仍连续，则采用架构方案；
- 若证据显示其他机制，更新两边结论。

## 四、C｜Implementation 角色

### 4.1 任务

依据已批准契约实现最小、可测试、可回滚的改动。

### 4.2 实施前必须提交

- patch scope；
- API/数据模型；
- 状态图；
- 失败路径；
- cancellation 语义；
- revision/invalidation 表；
- 内存/线程预算；
- 测试清单；
- 迁移与回滚。

### 4.3 编码约束

- 不在同一 PR 顺带重构无关代码；
- 不用 sleep 修复竞态；
- 不用无限队列；
- 不吞掉异常/错误；
- 不把正常 cancel 写成 failure；
- 不把 provider terminal 与 render ACK 混为一个事件；
- 不用裸 slot index 作为持久身份；
- 不在 QML 拼接业务状态机；
- 不把 trace 当同步机制；
- 不为了测试加入 production-only 不安全后门。

### 4.4 测试顺序

1. 先提交失败测试或可独立运行的 repro；
2. 实现最小行为；
3. 单元测试；
4. 组件测试；
5. deterministic event permutation；
6. UI contract；
7. hardware/pixel/perf；
8. soak；
9. 删除临时兼容/feature flag（若本批次应删除）。

### 4.5 Patch Manifest

```text
Changed contracts:
Changed invariants:
New state:
Removed state:
New threads/workers:
New queues and capacity:
New caches and byte limit:
Settings/schema migration:
Telemetry:
Tests:
Known limitations:
```

## 五、D｜Independent Correctness Review 角色

### 5.1 任务

不以“测试都过了”为终点，独立证明实现符合契约。

### 5.2 审查层次

#### 类型与不变量

- 非法状态是否可构造；
- identity/revision 是否完整；
- overflow/underflow；
- frame/time conversion；
- optional/missing 语义；
- exactness/domain 标注。

#### 状态机

- 每个状态的合法事件；
- 迟到事件；
- 重复事件；
- 事件顺序交换；
- cancellation；
- shutdown；
- rollback；
- exactly-once terminal。

#### 并发与生命周期

- worker/sink 所有权；
- detach/join；
- mutex/condition wait；
- GUI/render 线程阻塞；
- callback 捕获；
- device generation；
- resource retirement；
- ABA/reuse 风险。

#### 媒体正确性

- B-frame display order；
- non-zero/negative start PTS；
- VFR；
- keyframe seek；
- source frame mapping；
- missing/duplicate；
- rotation/SAR/color；
- hardware/software parity。

#### UI 投影

- Q_PROPERTY change notification；
- stale QVariant/model；
- focus/input context；
- busy/enabled；
- rollback；
- Accessibility。

### 5.3 必须独立运行的检查

- 阅读完整 diff，而非只看实现者摘要；
- 搜索新增类型所有使用点；
- 搜索旧 API 是否残留；
- 执行 targeted tests；
- 执行至少一个实现者未提供的 adversarial test；
- 检查 trace 中 command/ACK/commit；
- 检查资源预算；
- 检查错误路径的用户反馈。

### 5.4 Review 结论

```text
Approved
Approved with non-blocking follow-ups
Changes required
Rejected: contract mismatch
Unverified: missing evidence
```

“Unverified” 不等于失败，但不能进入 Final Verification。

## 六、E｜Regression / Edge-case Review 角色

### 6.1 任务

从组合场景、历史回归和边界值攻击改动。该角色不只测试新功能，而是找“新功能与旧功能相交”时的破坏。

### 6.2 必测组合

- 1/2/3 source；
- Reference=Timeline Master / 不同；
- Pair 包含/不包含 master；
- source add/remove/reorder/replace；
- Ready/Loading/Playing/Seeking/Scrubbing/Analyzing；
- CFR/VFR/non-zero PTS/B-frame；
- same/different fps/duration/resolution/rotation/SAR/color；
- hardware/software decode；
- device loss；
- fullscreen/chrome/inspector/dialog/menu；
- 100～250% DPI；
- duplicate input/held key；
- cancel/shutdown；
- file changed/deleted/locked；
- low memory/backpressure；
- event order permutations。

### 6.3 历史回归清单

每个相关改动必须重新覆盖：

- 持久化 0-2/1-2 Pair 在两路中黑屏；
- Wipe 旋转/UV/padding；
- render failure 错误 ACK 黑帧；
- input focus 导致快捷键误触；
- transport binding loop/高度塌缩；
- Reference/Pair normalization；
- step cancel 被错误显示为 lastError；
- range loop command 失败后状态悬挂；
- thumbnail late result；
- source changed-on-disk identity；
- device generation stale resource；
- marker 截断/密集渲染。

### 6.4 输出

Regression reviewer 提供风险分级：

```text
R0 Release blocker：数据/帧错误、崩溃、stale commit、partial FrameSet
R1 High：核心交互失效、不可恢复黑屏、严重性能退化
R2 Medium：可恢复错误、可访问性/布局回归
R3 Low：文案、非阻断视觉问题
```

每项包含 fixture、步骤、预期、实际、trace/screenshot。

## 七、F｜Final Verification 角色

### 7.1 任务

只对候选发布 SHA 做最终验收。不得用“PR 上某次通过”替代发布 commit。

### 7.2 前置条件

- Architecture 已批准；
- Root-cause 有确定结论；
- Implementation manifest 完整；
- Correctness review 无阻断；
- Regression review R0/R1 清零；
- 所有变更已合并，工作区干净；
- release SHA、tag、version 一致。

### 7.3 验证序列

1. clean configure/build；
2. unit/component/e2e；
3. architecture/format/lint；
4. Linux core；
5. Windows debug/release；
6. D3D11 hardware；
7. pixel capture；
8. playback/navigation performance；
9. fault injection；
10. shutdown/resource soak；
11. package/MSI install/upgrade/uninstall；
12. signature/hash/SBOM；
13. evidence bundle；
14. manual critical journey。

### 7.4 最终报告

```text
Candidate SHA:
Tag/version:
Environment:
Automated suites:
Hardware suites:
Performance comparison:
Pixel/golden comparison:
Soak:
Packaging:
Open risks:
Release decision:
Evidence manifest hash:
```

## 八、冲突裁决协议

### 8.1 冲突类型

- 事实冲突：“Reference change 是否会改变 timeline”；
- 机制冲突：“顿挫来自 decoder 还是 coordinator”；
- 方案冲突：“重构/补丁/替换 backend”；
- 阈值冲突：“P95 应设多少”；
- 产品冲突：“默认逐帧完整还是实时”。

### 8.2 裁决步骤

#### 步骤 1：写成可证伪命题

错误：

```text
方案 A 更好。
```

正确：

```text
在 fixture X、输入 30 Hz held backward、1080p60 H.264 GOP 120 下，
Reverse Window 会使 exact_seek_delta ≤ 2、sequence_errors = 0，
且 frame budget peak ≤ 256 MiB。
```

#### 步骤 2：定义控制变量

- exact commit；
- 同一 fixture；
- 同一机器/GPU/driver；
- 相同进程优先级/affinity；
- 冷/热缓存分别测试；
- 至少记录分位数和原始 trace。

#### 步骤 3：构造最小实验

优先顺序：

1. 纯单元状态机；
2. fake provider/renderer；
3. synthetic media；
4.真实硬件；
5. 用户真实样本。

#### 步骤 4：预先写判定规则

实验前写明什么结果支持/否定每个方案，避免看到结果后移动目标。

#### 步骤 5：复跑与独立复核

- 至少冷启动/热启动；
- 重复运行；
- 异常样本保留；
- reviewer 检查原始数据；
- 不只比较均值。

### 8.3 无法裁决时

- 降低改动范围；
- 保留旧默认并把新行为置于显式 experimental flag；
- 增加 telemetry；
- 不把未验证方案设为默认；
- 在风险登记中写明失效条件。

## 九、审查 Gate 清单

### Architecture Gate

- [ ] 单一 owner
- [ ] 完整 identity/revision
- [ ] FrameSet/ACK 不变量
- [ ] 有界资源
- [ ] 失败回滚
- [ ] 依赖方向
- [ ] 迁移路径

### Root-cause Gate

- [ ] 可重复最小复现
- [ ] 首个不变量违例
- [ ] 非原因已排除
- [ ] trace/test 证据
- [ ] 置信度与边界

### Implementation Gate

- [ ] 红测先行
- [ ] exactly-once terminal
- [ ] cancellation/failure 分离
- [ ] stale rejection
- [ ] telemetry
- [ ] schema/cache migration
- [ ] 无临时无限资源

- [ ] 独立 adversarial test
- [ ] 事件排列
- [ ] lifecycle/shutdown
- [ ] media timing

- [ ] 历史 Bug

- [ ] exact release SHA
- [ ] clean build

- [ ] evidence bundle

## 十、角色输出质量标准

一份合格报告必须让未参与实现的人能够：

1. 知道问题是什么；
2. 用给定 fixture 复现；
3. 看懂预期不变量；
4. 知道改了哪些边界；
5. 独立运行测试；
6. 从 trace/pixel/perf 判断结论；
7. 知道结论何时会失效；
8. 在回归时快速定位责任层。

这套协议的价值不在于“Agent 数量多”，而在于让架构、根因、实现、证明、攻击和发布六种思维不被同一个先入结论吞并。最终裁决始终落回代码与可复现实验。
