# 11｜关键架构决策与备选方案比较

## 核心结论

推荐方案是：**保留当前 C++/FFmpeg/D3D11/FrameSet 核心，以契约优先的增量重构修正语义与状态所有权。**
不推荐推倒重写，不推荐用 Qt Multimedia 替换媒体内核，也不推荐让多个独立播放器靠 UI 时钟同步。第三方内核如 libmpv 可以作为未来“通用播放兼容后端”的实验选项，但不能成为专业多源比较主路径，除非它能满足同一 FrameSet、精确帧身份、完整 ACK 和分析溯源契约。

---

## 一、候选总体方案

| 方案 | 正确性风险 | 交付风险 | 复用现有资产 | 多源帧准确性 | 长期可扩展性 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| A. 继续局部补丁 | 高 | 中 | 高 | 中 | 低 | 只适合紧急热修 |
| B. 契约优先增量重构 | 低～中 | 中 | 很高 | 高 | 高 | **推荐** |
| C. 全量重写 | 很高 | 很高 | 低 | 未知 | 理论高、实际不确定 | 拒绝 |
| D. Qt Multimedia 替换 | 高 | 中 | 低 | 低 | 中 | 拒绝主路径 |
| E. 多个独立 mpv/Qt player 同步 | 很高 | 中 | 低 | 低 | 低～中 | 拒绝 |
| F. libmpv 单后端 + 自建同步层 | 中～高 | 高 | 中 | 未证明 | 中 | 仅研究分支 |
| G. 双后端：专业核心 + 通用播放 | 中 | 很高 | 高 | 专业路径高 | 高但成本大 | 中长期可选 |

## 二、ADR-001：保留单一串行媒体真相

### Decision

所有 Session、Playback、Navigation、Alignment、Comparison selection 的 authoritative commit 继续经过一个串行协调边界。可以拆内部 workflow 和 worker，但不能新增第二个可独立写 snapshot 的 event loop。

### Rationale

现有最重要资产是：

- complete canonical FrameSet；
- Presentation ACK 后提交；
- session/epoch/generation/request 身份；
- provider/render/device 隔离；
- stale result rejection。

若多个工作流可并行写状态，会重新引入 A/B/C 不同帧、迟到结果覆盖和命令终态丢失。

### Rejected

- 每个 Source 一个 player/controller，各自发当前帧；
- QML 监听多个 position 后“尽量对齐”；
- analysis worker 直接更新 UI authoritative frame；
- renderer 自行推进 frame。

### Consequence

`PlaybackCoordinator` 需要瘦身，但仍保留最终串行提交职责。文件变小不是通过复制多个 coordinator 达成。

## 三、ADR-002：Reference 与 Timeline Master 分离

### Decision

`ReferenceSource` 表示业务 GT/基准；`TimelineMaster` 只定义 canonical timeline。两者可以相同，也可以不同。

### Rationale

“谁是 GT”和“谁定义帧编号/时间线”是两件事。绑定会使切换 GT 改变 frame count/time mapping/range，增加用户不可见副作用。

### Alternative

仍让 Reference 自动成为 canonical，但 UI 改名。

### Why rejected

这只是改文案，不消除行为耦合。多候选、固定 GT、不同质量 timeline 时仍会失败。

### Migration

- 旧 session 读取时令 TimelineMaster = 旧 Reference；
- 后续 SetReference 不再重建 timeline；
- SetTimelineMaster 是独立、显式、带位置 remap 的命令。

---

## 四、ADR-003：SourceKey 是稳定身份，RenderSlot 只是投影

### Decision

所有跨拓扑/异步/持久化/分析状态使用 `SourceKey`；固定 0/1/2 只在 renderer 边界短暂存在。

### Rationale

Slot 会因 add/remove/reorder/pair switch 改变。把 slot 用作身份导致历史上持久化 Pair 和两路/三路切换错误。

### Alternative

继续 SourceId 整数，但保证永不复用。

### Why not preferred

进程内单调 SourceId 可以工作，但 workspace、file replacement、跨会话 cache 和导出仍需要稳定、可序列化且不依赖创建顺序的身份。可以把 SourceId 作为 runtime handle，SourceKey 作为业务 identity。

---

## 五、ADR-004：会话 Pair 不进入全局 Preferences

### Decision

Preferences 只保存默认 Pair 策略；具体 Pair 存于当前 session/workspace。

### Rationale

“上次三路会话选择 0-2”对下一次两路会话没有稳定含义。全局 ordinal 会在 topology 改变后变成陈旧意图。

### Alternative

继续持久化 edge，并在 source count 改变时 normalize。

### Why rejected

Normalize 只能防黑屏，不能保证恢复的是用户原本想比较的源；第三路恢复后旧 edge 又会复活，状态不可解释。

---

## 六、ADR-005：播放工作负载显式分离

### Decision

Exact Seek、Forward Step、Reverse Step、Realtime Play、Scrub、Range 是不同 workflow/strategy。

### Rationale

它们对以下问题答案不同：

- 是否关心中间帧；
- 是否允许跳；
- 是否 latest-wins；
- 是否需要 decoder cursor；
- 是否需要 wall-clock；
- 取消后恢复什么；
- 缓存方向；
- 命令终态。

### Alternative

在 `beginSeek()` 或 `PlaybackRun` 中不断增加 if/flag。

### Why rejected

状态组合会指数增长，最终无法证明某个 flag 组合的事件顺序。共享 `FramePresentationTransaction` 即可复用正确性，不需要共享整个状态机。

---

## 七、ADR-006：反向逐帧使用有界 GOP Window

### Decision

从随机访问点正向解码窗口，再以反向显示顺序消费。预算不足时退化 Exact。

### Alternatives

1. 每次 -1 Exact Seek；
2. 无限缓存已看过帧；
3. 尝试 FFmpeg “倒放”；
4. 预先生成反向代理。

### Comparison

| 方案 | 首次延迟 | 连续体验 | 内存 | 原媒体精确 | 实施成本 |
|---|---:|---:|---:|---:|---:|
| 每帧 Exact | 高 | 差 | 低 | 高 | 低 |
| 无限历史缓存 | 低（已看过） | 好 | 不可控 | 高 | 中 |
| GOP Window | 中 | 好 | 有界 | 高 | 中～高 |
| 反向代理 | 高预处理 | 好 | 磁盘高 | 可控 | 高 |

GOP Window 是专业播放器的合理折中。

---

## 八、ADR-007：Range Loop 属于 Application

### Decision

闭区间边界、loop 重锚、VFR 映射由 Application playback workflow 拥有；QML 只设置 In/Out/loop。

### Rationale

UI 事件延迟不能证明“不越过 Out”。Range 是媒体时钟约束，不是视觉便利功能。

### Alternative

继续在 `onCurrentFrameChanged` 发 seek，并补更多标志。

### Why rejected

依赖投影信号与命令往返，和 RealTime catch-up/ACK 排列交叉后难以证明。

---

## 九、ADR-008：Scrub 使用预览状态，不修改 authoritative frame

### Decision

UpdateScrub 返回独立 preview；Commit 后精确 ACK 才改变 displayedFrame。

### Rationale

用户需要即时反馈，但预览可以降级、跳过和 latest-wins；authoritative frame 不能有这些语义。分开后既流畅又不欺骗。

### Alternatives

- 每次 pointer move 普通 seek；
- 只显示时间码、永远无画面；
- UI 自己缓存 scene graph。

普通 seek 会造成取消风暴；纯时间码体验不足；scene graph cache 只覆盖已看过帧。

---

## 十、ADR-009：实时 renderer 与整段分析分离

### Decision

Renderer 负责当前 FrameSet 的低延迟视觉结果；Sequence Analysis 使用独立 worker/port，不从 render thread 回读整段数据。

### Rationale

把 PSNR/SSIM/统计 reduction 塞入每帧 render 会：

- 增加 presentation latency；
- 阻塞 ACK；
- 混淆实时/离线优先级；
- 让分析失败影响播放；
- 难以取消和缓存。

当前帧简单 metric 可用 GPU，但整段工作独立调度。

---

## 十一、ADR-010：N 个逻辑源，有限活动呈现集

### Decision

Session 可管理 N 个源；每次实时 FrameSet 只包含有限活动集合。

### Rationale

专业工作流通常是“GT 与当前 Candidate”而不是同时盯 16 个小窗。有限活动集保护：

- 帧原子性；
- 解码/GPU 预算；
- UI 清晰度；
- 慢源隔离；
- Pair 切换事务。

### Alternative

把所有固定数组改 vector，FrameSet 包含 N 路。

### Why rejected

任何一路延迟都会阻塞整组；资源按 N 线性增长；Pair 仍是 N²；用户并不能有效审查大量小窗。

---

## 十二、ADR-011：不采用 Qt Multimedia 作为专业核心

### 可取之处

- 集成简单；
- 平台播放能力；
- 音频/字幕基础；
- 较少自维护 FFmpeg 代码。

### 不满足的关键要求

- 多源同一 canonical FrameSet；
- 物理显示帧身份；
- 自定义 alignment mapping；
- 受控 exact/sequential/reverse 解码；
- D3D11 资源/ACK 生命周期；
- exact plane difference；
- deterministic hardware gates；
- per-source diagnostics/provenance。

可以在未来为“快速预览不支持格式”做隔离实验，但不能替换主路径。

---

## 十三、ADR-012：不采用多个独立播放器同步

### 问题

即使所有播放器都 seek 到相同时间：

- keyframe/rounding 不同；
- VFR frame choice 不同；
- decoder queue/clock 不同；
- presentation 不同刷新；
- 无法原子提交；
- 一路失败时其他路继续；
- UI 看见撕裂式对比；
- 分析无法确认实际比较帧。

软件“看起来同步”不等于有可证明的 frame identity。

---

## 十四、libmpv 方案的边界

libmpv 是成熟播放器内核，通用 codec、音频、字幕、HDR 能力很有吸引力。但作为 Toy 主内核，需要先用原型验证：

1. 能否稳定请求/确认精确 display-order frame；
2. 能否控制 1～3 路在一个外部事务中原子呈现；
3. 能否拿到原生 plane/GPU resource 做 exact diff；
4. hardware decode 与 Qt/D3D11 context 互操作；
5. cancellation/stale identity；
6. VFR/alignment source-frame mapping；
7. distribution/license；
8. 性能和资源预算。

若不能满足，最合理的用法是：

```text
Professional Review Backend（现有核心）
Generic Playback Backend（libmpv，可选）
```

但双后端会使 UI、settings、测试和支持矩阵翻倍，不进入当前关键路径。

## 十五、重写方案为什么错误

全量重写常见理由：

- 大文件太多；
- 历史补丁复杂；
- 想支持更多功能；
- 新架构“更干净”。

但 Toy 已经积累最难重建的部分：

- 时序与身份；
- FrameSet 原子性；
- VFR/B-frame；
- D3D11VA/zero-copy；
- device generation；
-大量故障/性能/像素测试；
-发布管线。

重写会把已知技术债换成未知正确性债，并在长时间内缺少可比较基线。推荐通过 façade、workflow、transaction object 逐层迁移。

只有出现以下证据才重新评估重写：

- 核心依赖已不可维护/停止支持；
- 现有架构无法表达目标且原型证明迁移成本更高；
- 有完整行为兼容 harness；
- 新实现可并行跑同一 fixtures 并逐项超过旧实现；
- 发布迁移和回滚明确。

当前证据不满足。

## 十六、默认产品取舍

### 优先

1. 帧准确与可解释；
2. 本地文件；
3. GT/候选多源评审；
4. 专业导航；
5. 差异与量化；
6. 稳定性、恢复和诊断；
7. Windows GPU 体验。

### 后置

- 网络流；
- DRM；
- 电视/直播；
- 媒体库；
- 插件商店；
- 大量字幕格式；
- 跨平台完整 UI；
- 云协作。

后置不代表永不支持，而是避免“最好”变成无边界的功能罗列。

## 十七、明确禁止的实现捷径

- 为流畅直接取消 ACK 后提交；
- 为同步让 UI 等待每路播放器；
- 为后退无限缓存；
- 为 N 源启动 N 个常驻高优先级 decoder；
- 为 Pair 继续增加 `Edge0And3` 枚举；
- 为统计从 renderer 同步 readback；
- 为修竞态增加固定 sleep；
- 为防 crash 吞掉所有异常；
- 为兼容把 unsupported/HDR 静默当 SDR；
- 为通过性能门禁放宽正确性指标；
- 为“简化”把 Reference 与 Timeline Master 再次绑定；
- 为快速上线让 QML 持有 range/scrub/analysis 生命周期。

---

## 十八、决策复审触发条件

ADR 不是永久真理。出现以下情况可复审：

- 目标用户从专业评审转为通用消费播放；
- 跨平台成为最高优先级；
- 新图形 API/媒体框架可证明满足完整契约；
- N 源实时墙成为核心需求；
- 音频/字幕远高于像素对比；
- 当前核心无法在目标媒体上达到硬性能；
- 维护数据表明 FFmpeg/D3D11 自有栈成本不可接受。

复审仍使用同一规则：先定义可证伪目标，以原型和相同 fixtures 对比，不靠偏好投票。

综合判断：**契约优先增量重构是风险最低、最能保留 Toy 独特价值、也最有机会真正做到“最佳专业视频播放器”的路线。**
