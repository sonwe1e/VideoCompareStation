# 02｜根因与缺陷调查

## 结论

当前最需要处理的不是零散视觉 Bug，而是五条会不断制造新 Bug 的根因链：

```text
语义身份被槽位序号替代
    → Pair/Reference/拓扑切换失真

多个工作负载共用同一导航路径
    → 前进快、后退慢、随机 seek 与逐帧互相取消

媒体状态落在 UI/Preferences
    → Range、比较选择、错误提示跨层耦合

高低频状态合并投影
    → Main.qml 与 ReviewController 组合复杂度持续增长

分析能力直接依附 renderer
    → 容易把可视化、量化和播放性能混在一起
```

本文件把问题分为：已由代码确认的缺陷/结构债、需要实验确认的高概率风险、以及产品能力缺口。处理顺序以“根因是否会污染后续设计”为准，而不是以 UI 是否显眼为准。

## 2. C-01：Reference 与 canonical timeline master 强耦合

### 2.1 现象

UI 提供 “Reference”“Make reference”“R” 标记；从用户视角，这通常表示：

- 作为 GT/基准；
- 在 Reference Focus 中更突出；
- Diff 默认与它比较；
- 量化指标以它为基准。

但当前 Domain 在验证时执行：

```cpp
const SourceId canonicalId = referenceId.value_or(sources.front().id);
```

`ValidatedComparisonSet` 还明确约定：有 Reference 时，它就是 canonical source。

因此切换 Reference 实际会同时改变：

- canonical timeline；
- frame count；
- frame rate/timing source；
- current MediaTime → FrameId 映射；
- In/Out remap；
- alignment 基准；
- `oneSecondStepFrames`；
- timecode；
- 可能的 VFR timeline index。

这比“更换基准画面”重得多。

### 2.2 根因

`ReferenceSourceId` 和 `TimelineMasterSourceId` 在最初双路设计中通常相同，因此被合并。项目扩展到三路、对齐、Range 和多模式后，这两个概念的变化频率和副作用已经不同，但类型没有分开。

### 2.3 为什么不能继续打补丁

在 QML 上改标签，或在 Reference 切换后多做一次 `remapRange()`，都不能消除根因。后续引入 GT + 多候选、指标、音频 master 时，耦合会更严重。

### 2.4 正确修复

引入三个独立状态：

```cpp
struct TimelineSelection {
    SourceKey master;
};

struct ComparisonSelection {
    std::optional<SourceKey> reference;
    ComparisonPair activePair;
};

struct FocusSelection {
    SourceKey focused;
};
```

- 改 `reference`：不重建 canonical timeline；
- 改 `activePair`：只改变 presentation/analysis selection；
- 改 `timeline master`：显式重建 timeline，并给出明显提示；
- UI 分别显示 “Timeline”“Reference”“Compare”。

## 3. C-02：Active Pair 被表示为全局 ordinal preference

### 3.1 现象

`DifferenceEdge` 只有：

```text
0↔1
0↔2
1↔2
```

`ReviewPreferencesController` 持久化该值。`ReviewController` 再生成“A ↔ B”等标签。两路会话中 shell 会把无效边投影为 0↔1，但保留原偏好，以便第三路恢复时重新生效。

这个机制已修复过一次严重回归：持久化 A/C 在两路会话里曾让 Wipe/Diff 黑屏。

### 3.2 根因

混淆了三类状态：

1. **用户通用偏好**：例如默认进入 Side-by-side；
2. **当前会话选择**：当前比较哪两条 Source；
3. **渲染槽位映射**：这两条 Source 在当前 FrameSet 中占 0/1/2 哪个 slot。

只有第 1 类适合进入全局 Preferences。第 2 类必须按稳定 SourceKey 保存；第 3 类只应存在于 presentation adapter。

### 3.3 额外 UX 问题

- 从三路临时删除 C 后，界面显示 A/B；重新加入第三路时可能突然回到旧 A/C；
- 文件被重新排序或更换后，A/C 不再代表原来两条媒体；
- “GT 对当前候选”无法用 ordinal 表达；
- 增加第四路会迫使枚举爆炸。

### 3.4 正确修复

```cpp
struct ComparisonPair {
    SourceKey first;
    SourceKey second;
};

enum class DefaultPairPolicy {
    ReferenceAndFirstCandidate,
    LastTwoActiveSources,
    PreserveIfAvailable
};
```

- Preferences 只保存 `DefaultPairPolicy`；
- Session 保存 `ComparisonPair`；
- renderer adapter 在每个 presentation revision 中把 SourceKey 映射为 compact RenderSlot；
- Pair 不可用时执行唯一、可测试的 fallback，并向 UI 报告原因。

## 4. C-03：连续逐帧只优化了 +1

### 4.1 现状

`PlaybackCoordinator::beginStep` 明确：

```cpp
if (command.delta == 1) {
    enqueueInteractiveForwardStep(command);
    return;
}
// backward / multi-frame jump → beginSeek(... Exact ...)
```

Provider 的 Sequential continuity 也要求：

```cpp
request.frameId > previousSequentialFrame
```

因此：

- 长按 Right/D：同一 generation、Sequential、read-ahead；
- 长按 Left/A：每个输入进入 Exact seek 语义；
- Shift+Left 的 -5：Exact；
- 往返检查边缘时，方向切换会拆掉前向 stream。

### 4.2 根因

v1.5/v1.6 的目标是解决最明显的“长按下一帧卡顿”，设计明确把反向列为 Exact 非目标。现在产品要继续提升，必须增加反向专用算法，而不是简单把负数也标记为 Sequential。

压缩视频无法天然反向解码。正确做法是：

```text
目标反向帧 N-1
  → 找到覆盖窗口的前置关键帧 K
  → 从 K 正向解码到 N
  → 将 [K..N] 放入有界 GOP/Window cache
  → 按 N-1, N-2... 反向提交完整 FrameSet
  → 到窗口左边界时预建前一个窗口
```

多源情况下每个 canonical frame 仍先完成映射与 FrameSet 组装，不能单路自行倒放。

### 4.3 验证指标

新增 held-backward profile：

- 300 次 `StepFrames(-1)`；
- 25–35 Hz deterministic jitter；
- 0 missing intermediate canonical FrameId；
- 0 stale commit；
- 0 partial FrameSet；
- warm-up 后 exact seek 数显著下降；
- decoder reopen = 0；
- memory budget 不超限；
- P95/P99 与 held-forward 差距在目标硬件基线内。

## 5. C-04 / H-01：Range Loop 在 QML

### 5.1 当前链路

`Main.qml::onCurrentFrameChanged`：

```text
如果 playing 且 currentFrame >= outFrame
    → shell.setRangeStartPending(true)
    → controller.seekFrame(inFrame)
当 currentFrame == inFrame 且 !busy
    → controller.play()
```

### 5.2 已确认的问题

- Range 的播放权威不在 `PlaybackRun`；
- QML 必须理解 seek/play 终态；
- Range 状态散落在 Shell 与 Main；
- 每圈都经历显式 seek 和重新启动；
- UI 关闭/焦点/状态投影都可能影响流程；
- v1.6 release note 已把“coordinator-native Range Loop”列为未完成项。

### 5.3 高概率越界风险

Playback 有 wall-clock catch-up。在某次 stall 后，它可能从 Out 前一帧直接选择 Out 后的 canonical target。QML 只能在该帧 ACK 并成为 `currentFrame` 后才发现 `>= Out`，此时范围外帧已经呈现。

这必须用 fake clock 和 deterministic renderer ACK 做红测试，不能靠肉眼判断。

### 5.4 正确修复

`PlaybackRun` 持有：

```cpp
struct PlaybackRange {
    FrameId in;
    FrameId out;       // inclusive
    bool loop;
};
```

选取下一 target 时先应用范围约束；到 Out：

1. 允许 Out 完整呈现；
2. 不产生 Out+1；
3. 预备或精确获取 In；
4. 重新锚定时钟；
5. 继续，不经过 QML seek/play 反馈环。

## 6. C-05：Timeline Thumbnail 不是按需缩略图

### 6.1 当前行为

`TimelineThumbnailCache.qml` 对 `sourceItem.grabToImage()`：

- 只在 `currentFrame` 变化时抓取当前已显示画布；
- 只保存约 120 个 sample；
- hover 未显示过的位置时没有图；
- popup 明确提示 “Preview caches during playback”。

### 6.2 根因

缩略图被当成 scene-graph screenshot cache，而不是媒体查询服务。它无法：

- 请求任意 target frame；
- 指定 Reference 或 active pair；
- 在未播放前生成；
- 与 Source fingerprint、timeline revision、color transform 建立可靠 cache key；
- 在播放压力高时调度优先级。

### 6.3 正确修复

新增低优先级 `IThumbnailProvider`，latest-wins、独立 decoder、目标尺寸解码、LRU、有身份取消。QML 只发 hover frame，不直接抓画布。

## 7. C-06 / H-02：状态投影过宽

`ReviewController::ReviewView` 包含：

- Source/URL/模型；
- session/busy/frame pending；
- playback/frame/timecode；
- 所有媒体信息和错误；
- alignment 状态、marker、progress；
- compatibility；
- difference edges；
- 所有 capability。

`Main.qml` 再从这个对象派生大量属性与字符串。虽然有 `sameFrameState` 优化和 `frameStateChanged`，但 façade 的 playback/alignment/notifications 仍指向同一 controller。

### 根因

当前 façade 只完成了命名边界，没有完成状态所有权迁移。

### 风险

- 高频帧更新可能使低频区域参与 binding 评估；
- 新增一个属性需要修改 controller、view、signal、QML；
- error/alignment/transport 的状态组合难以局部证明；
- 测试必须实例化大对象。

### 修复顺序

不要一次拆完。先按最容易制造语义 Bug 的顺序：

1. `ComparisonViewModel`
2. `TimelineViewModel`
3. `PlaybackViewModel`
4. `DiagnosticsViewModel`
5. `AlignmentViewModel`
6. `SessionViewModel`

每个 ViewModel 只读一个 typed sub-snapshot，并只发本 capability 的命令。

## 8. C-07：隐藏式播放策略

当前 playback 在短于 2 秒的延迟内继续呈现每个 canonical frame；超过阈值后根据 wall clock 跳过完整 FrameSet 追赶。

技术上这是合理折中，但对专业用户有两个问题：

- 无法预测当前是在“保每帧、变慢”还是“保实时、丢完整帧集”；
- 性能统计中的 dropped sets 和主观体验没有明确模式语义。

应显式建模：

```cpp
enum class PlaybackPolicy {
    ReviewEveryFrame,  // 不跳，允许时钟滑移
    RealTime,          // 允许跳完整 FrameSet
    Contextual         // 单源默认 RealTime，多源默认 ReviewEveryFrame
};
```

状态栏必须显示实际策略和 dropped/late 计数。

## 9. C-08：键盘与辅助功能缺口

### Wipe

`WipeHandle.qml` 有 Drag/Tap/Hover，但没有：

- `activeFocusOnTab`
- `Accessible.role = Slider`
- min/max/current value
- Left/Right 或 Up/Down 调节
- orientation 描述

### Timeline

`TimelineTracks.qml` 设置了 Slider role/name 和 Tab focus，但没有看到：

- `Accessible.value/minimumValue/maximumValue`
- `Keys.onLeft/Right/Home/End/PageUp/PageDown`
- focused/dragging 状态的读屏反馈。

这不是“附加美化”，而是所有自定义控件必须满足的输入契约。整改时应建立自动 accessibility contract test。

## 10. C-09：三路硬编码不是简单上限

三路限制同时存在于：

- Domain validator 的 `kMaximumSources = 3`；
- `std::array<..., 3>`；
- `sourceA/B/C` property；
- `DifferenceEdge` 三条边；
- QML Source A/B/C model；
- renderer layout；
- hardware performance profile。

因此，直接把常量改成 8 会破坏：

- FrameSet 内存与 decode 并发；
- UI property contract；
- Pair 枚举；
- renderer slot layout；
- cache budget；
- performance gate。

正确模型是：

```text
LoadedSources = N（逻辑会话）
ActivePresentationSet = M（当前实时解码/呈现，先保持 M≤3 或 M≤4）
ActivePair = 2
BackgroundAnalysisSet = 可批处理
```

只有这样才能支持 GT + 多候选，而不要求 16 路同时 120 fps 解码。

## 11. C-10/C-11/C-12：信息表达问题

### Reference 标签

同一控件同时出现 “Reference”“Canonical reference source”“Make reference”，没有告诉用户它会重建时间线。整改前至少要改成 “Timeline & Reference” 并显示副作用；完成语义分离后改为独立控件。

### Source 上下文

Active Source Strip 会显示 `A · filename`，但 Wipe/compact/fullscreen 往往只显示字母。专业评审中多个文件名可能只有后缀差异，字母不足以确认当前 pair。

应提供：

- 会话内 alias；
- role badge：GT/Reference/Candidate；
- compact label：`GT`、`C1`、`C2`；
- hover/OSD 显示完整文件名和 fingerprint 状态；
- active pair 始终在状态栏可见。

### 状态反馈

当前有：

- full overlay；
- frame pending bubble；
- alignment banner；
- analysis badge；
- toasts/intents；
- error banner；
- Main.qml 拼接的 combined status。

应统一为有优先级的 typed status rail，避免多个层同时争夺画布。

## 13. 根因调查完成标准

一项问题只有在以下证据齐全后才可标记“已解决”：

```text
最小复现测试（修复前红）
+ 根因说明
+ 最小职责边界内的实现
+ 单元/组件/硬件测试（修复后绿）
+ 回归矩阵
+ 性能/内存对比
+ 用户可见行为说明
```

“看起来不再出现”“增加 if 防御”“测试跑过一次”均不构成完成。
