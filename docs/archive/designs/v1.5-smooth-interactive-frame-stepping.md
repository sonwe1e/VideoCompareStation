# VCStation 1.5 — Smooth Interactive Frame Stepping

**Target baseline:** `main` @ `a66b1e7fb793c7f94cf35c8d43e476d85b614091`  
**Primary problem:** holding Next/Right/D on a single video feels visibly jerky compared with mature desktop players.  
**Status:** implementation-ready design.  
**Priority:** P0 for v1.5.

---

# 核心结论

当前“长按下一帧”卡顿的首要原因不是 D3D11 绘制，也不是简单的缓存容量不足，而是 **交互逐帧被实现成了连续 Exact Seek 的取消/重启风暴**。

当前链路大致为：

```text
OS keyboard auto-repeat
    ↓
ReviewShortcuts.qml
    ↓
ReviewActions.nextFrame()
    ↓
ReviewController::next()
    ↓
StepFramesCommand(+1)
    ↓
PlaybackCoordinator::beginStep()
    ↓
beginSeek()
    ↓
cancel(currentPlaybackScope)
playbackGeneration++
FrameRequestPriority::Exact
    ↓
新按键 repeat 到来
    ↓
supersedePendingSeek()
cancel(previous provider request)
cancel(previous presentation timer)
    ↓
再次 beginSeek()
```

这套逻辑对于“用户快速点几次，只关心最终目标帧”的交互是合理的，但对于“按住下一帧，希望连续看到每一帧”的交互是错误的。

它会造成：

1. FFmpeg 的 forward decode continuity 被频繁打断；
2. 前一个 Exact decode 尚未完成就被 cancel；
3. decoder 可能进入 interrupt / reopen / seek / flush 路径；
4. `playbackGeneration` 被高频递增，导致已有预取和连续上下文快速失效；
5. 每次 repeat 都重新建立完整的 exact frame transaction；
6. Exact prefetch 还没来得及产生收益，就被下一次 repeat 打断；
7. UI、Coordinator、Provider、Decoder、Render ACK 全链路发生比“正常播放”高得多的控制面抖动。

项目现有正常播放已经证明了正确方向：`Sequential` request、持久 decoder cursor、read-ahead、prepared successor、presentation ACK 后提交。v1.5 不应该发明新的解码器，而应该让“连续 +1 帧交互”复用这条已有快路径。

# 1. 当前实现为什么会顿挫

## 1.1 输入层不是主要问题

`ReviewShortcuts.qml` 的 `D` / `Right` 最终不断调用 `ReviewActions.nextFrame()`。

系统按键自动重复本身会产生一串离散事件，但成熟播放器通常不会把每个事件都解释为一次“随机定位事务”。它们会尽量保持同一个 demux/decoder 的 forward cursor，并消费已经解码或即将解码的后继帧。

因此 v1.5 不需要首先改键盘 repeat 频率，也不应该依赖 QML 定时器模拟播放。

## 1.2 `beginStep()` 最终无条件进入 Exact Seek

当前 `PlaybackCoordinator::beginStep()` 会根据 `requestedFrame` 链式计算目标：

```cpp
current = requestedFrame.value_or(displayedFrame);
target = current + delta;
beginSeek(command.context, target);
```

这解决了“快速按 3 次应该走到 N+3”的目标累积问题，但每次都会进入 `beginSeek()`。

`beginSeek()` 会：

- `directFrameProvider->cancel(currentPlaybackScope())`
- `playbackGeneration++`
- 创建新的 pending seek
- 提交 `FrameRequestPriority::Exact`

因此连续 `+1` 并没有被识别为“连续解码”，而是被当成了 N、N+1、N+2、N+3 四次独立随机 seek。

## 1.3 新 repeat 会主动取消旧 seek

Command dispatch 还会在新 navigation 到来时调用 `supersedePendingSeek()`。

这意味着长按过程中不是“排队处理连续帧”，而是：

```text
decode N+1
  ↳ cancel
decode N+2
  ↳ cancel
decode N+3
  ↳ cancel
decode N+4
...
```

当 H.264 / HEVC / MPEG-4 GOP 较长、B-frame 较多、硬件/软件 decoder 正在等待 packet/frame 时，这种取消模式非常容易产生肉眼可见的节奏断裂。

## 1.4 媒体层其实已经有正确的快路径

当前 `MultiSourceFrameProvider` 已经具备：

```text
Exact queue       = 1
Sequential queue  = 2
Prefetch queue    = 8
```

Sequential request 会在连续条件成立时设置：

```cpp
continueSequentially = true;
readAheadCount = 3;
```

`SourceDecodeActor` 也已经支持：

```cpp
decodeExact(...)
decodeSequential(...)
```

并且 `decodeSequential()` 能保留 decoder/demux cursor，避免相邻 forward frame 每次重新 seek + flush。

更重要的是，如果一次 `Sequential` request 没有可复用的连续游标，现有 actor 仍可以回退到 Exact decode。也就是说：

> **“把 forward +1 step 提交为 Sequential”不会牺牲精确 FrameId；它只是在条件允许时绕开不必要的 seek/flush。**

## 1.5 正常 Play 已经用了 `frame + preparedFrame`

`PlaybackCoordinator` 的正常播放链路已经有：

```text
current playback frame
prepared next playback frame
```

而且会在当前帧提交时预备下一帧。

因此 v1.5 最值得复用的不是“Play 命令本身”，而是以下四个机制：

- 同一 generation 内的 Sequential request；
- decoder continuity；
- 下一帧预备；
- Render ACK 后才更新 displayedFrame。

# 2. v1.5 目标

v1.5 的目标不是把“长按下一帧”变成隐藏的 Play，而是新增一个明确的 **Interactive Forward Step Stream**。

它需要满足：

1. 单击 Next 仍然得到精确的下一物理显示帧；
2. 连续 `+1` 输入不再重复 cancel / generation++ / exact seek；
3. forward step 在 decoder continuity 可用时走 Sequential；
4. continuity 不可用时自动 Exact fallback；
5. 每一个实际呈现的帧仍经过完整 FrameSet + Presentation ACK；
6. 不跳帧；
7. 不允许一个 source 比另一个 source 先提交；
8. 不阻塞 GUI thread；
9. 不阻塞 render thread；
10. 随机 seek、反向 step、First、Last、alignment rebuild 等仍保留 Exact 语义；
11. 对 1-source 优先达到显著收益，但实现保持 1–3 source 通用；
12. 不通过无限扩大缓存换流畅度。

# 3. 推荐架构：Forward Step Stream

## 3.1 不增加新的 QML 播放时钟

继续允许操作系统产生按键 auto-repeat：

```text
D / Right repeat
    ↓
StepFramesCommand(+1)
```

区别只发生在 Application 层。

这样有三个优点：

- 不需要可靠检测 key release；
- 鼠标点击、键盘、未来 jog controller 都能复用同一语义；
- 不把媒体节奏迁移到 QML。

## 3.2 连续 `+1` 不再进入 `beginSeek()`

新增内部状态：

```cpp
struct PendingInteractiveStep {
    CommandContext command;
    PendingPlaybackFrame frame;
};

struct InteractiveStepRun {
    PlaybackRequestContext providerContext;

    // 当前已经提交到 renderer / 正在等待 provider+presentation 完成的帧。
    std::optional<PendingInteractiveStep> frame;

    // 已经在 provider/decoder 侧提前准备，但尚未进入 renderer 的后继帧。
    std::optional<PendingInteractiveStep> preparedFrame;

    // 用户输入允许领先 displayedFrame 的目标。
    std::deque<CommandContext> queuedCommands;

    domain::FrameId lastQueuedTarget;
};
```

名字可以进一步抽象，但语义必须独立于 `PlaybackRun`。

**不建议直接把 Interactive Step 强塞进现有 `PlaybackRun`。**

原因是：

- realtime playback 允许根据 wall clock catch-up；
- interactive step 必须保证逐帧不丢；
- realtime playback 有 Play/Pause 可见状态；
- interactive step 对用户仍应表现为 paused frame review；
- 两者失败/停止语义不同。

可以抽取公共的 `PendingSequentialFrame` 辅助结构，但不要共用整个状态机。

# 4. Forward Step Stream 的核心状态机

## 4.1 第一次 `+1`

当收到：

```cpp
StepFramesCommand{ .delta = 1 }
```

并且当前没有 forward step stream：

1. 验证 Ready / graphics / frame boundary；
2. 若 active Play 存在，按当前规则先 Stop Play；
3. 若存在 incompatible Exact navigation，先 cancel + invalidate；
4. **只在 stream 建立时递增一次 `playbackGeneration`**；
5. 创建 `InteractiveStepRun`；
6. 目标 = `displayedFrame + 1`；
7. 提交：

```cpp
FrameRequestPriority::Sequential
```

此时如果 provider 没有连续游标，它会自行走 Exact fallback。

## 4.2 第二次及后续 `+1`

如果 forward stream 仍然活跃：

**禁止：**

```cpp
supersedePendingSeek()
cancel(providerContext)
playbackGeneration++
```

而是：

```text
lastQueuedTarget++
```

并把该 command 绑定到对应 target。

只允许有限前压。

建议：

```cpp
constexpr std::size_t kInteractiveStepInputLookahead = 3;
```

含义不是 decoder cache 只有 3 帧，而是：

> 用户输入目标最多领先已呈现帧 3 帧。

这样即使 OS auto-repeat 比 decode 快，也不会形成几十帧的 release 后拖尾。

如果达到上限，新 `StepFrames(+1)`：

```text
complete CommandOutcome::Busy
```

而不是继续堆积。

下一次键盘 repeat 会再次尝试。

## 4.3 Provider Pipeline

stream 最多保持：

```text
1 current + 1 prepared
```

与现有 playback pipeline 相同。

同时 `SourceDecodeActor` 保留现有：

```text
readAheadCount = 3
```

因此整体是：

```text
Renderer:
    N

Provider operation:
    N+1

Prepared operation:
    N+2

Decoder internal cache:
    N+2 / N+3 / N+4 ...
```

不要把 provider Sequential queue 从 2 盲目扩大到 8。

当前 2 个 operation + decoder read-ahead 已经能覆盖 pipeline latency，而且不会让停止/切 seek 时积累大量废弃 work。

# 5. Commit 语义

Interactive step 的一帧仍然必须满足：

```text
FrameSetReady
+
RequestSucceeded
+
FrameSetPresented ACK
```

三者全部匹配当前 `FrameRequestContext` 后才允许：

```cpp
state_.displayedFrame = target;
```

并完成对应的 `StepFramesCommand`。

这条规则不能为了“更顺”而放松。

## 5.1 `requestedFrame`

建议 `requestedFrame` 表示 stream 中最后一个已接收目标。

例如：

```text
displayed = 100
current   = 101
prepared  = 102
queued    = 103

requestedFrame = 103
```

这保留了现有 UI “frame pending” 的含义。

但中间帧 101、102 仍然全部呈现，绝不能从 100 直接跳 103。

## 5.2 Stream Drain

当：

```text
current == none
prepared == none
queued == empty
```

stream 自然结束：

```text
playbackState = Paused
requestedFrame.reset()
```

**不要主动 cancel decoder/provider playback scope，也不要递增 generation。**

原因：

stream 已经没有异步工作需要取消，而保留同 generation 可以让下一次 `+1` 继续使用 warm sequential cursor / read-ahead cache。

只在发生 discontinuity 时 invalidate：

- backward step；
- seekFrame(random target)；
- First / Last；
- Play；
- source topology change；
- alignment mapping revision；
- device generation change；
- close/shutdown；
- decode failure。

# 6. 为什么单击也可以走 Sequential Priority

v1.5 可以让所有 `delta == +1` 的 Step 使用 Sequential request，而不只识别“长按”。

这是推荐方案。

原因：

```text
Sequential priority
≠
必须假设 decoder 已经连续
```

现有 Provider 会检查：

```cpp
sequentialSetReady_
&& sequentialSetFrame_.has_value()
&& request.frameId > sequentialSetFrame_
```

只有满足条件才 `continueSequentially = true`。

否则当前 SourceDecodeActor 仍然能走 Exact decode。

因此行为变成：

```text
第一次 +1：
    sequential priority
    → continuity unavailable
    → Exact fallback
    → 精确拿到 N+1

第二次 +1：
    sequential priority
    → continuity available
    → decodeSequential(N+2)

第三次 +1：
    decodeSequential(N+3)
...
```

这比在 UI 上识别“单击/长按”更可靠。

# 7. 绝对不要采用的方案

## 7.1 不要简单扩大缓存

当前已经存在：

- 224 MiB playback frame budget；
- 12 MiB/source cache；
- 96 MiB FrameSet cache；
- Sequential read-ahead = 3；
- Provider sequential queue = 2。

长按卡顿发生在 request cancellation / Exact path 上。

扩大缓存并不能修复：

```text
cancel → generation invalidation → seek/flush/reopen
```

反而会提高：

- GPU/CPU frame residency；
- 4K/P010 峰值内存；
- cancellation cleanup；
- device loss retirement 压力。

## 7.2 不要把 Next 长按直接映射成 Play

Play 允许 wall-clock catch-up，并在严重落后时跳完整 FrameSet。

逐帧审查的长按 Next 应保证：

```text
100 → 101 → 102 → 103
```

而不是：

```text
100 → 101 → 104
```

## 7.3 不要移除 Presentation ACK

如果 displayedFrame 在 GPU 真正展示前就更新，会造成：

- timeline 与画面不同步；
- source mapping 与画面不同步；
- command terminal 提前；
- A/B/C 原子性破坏。

## 7.4 不要用 QML 16 ms Timer 调 next()

项目旧设计已经明确证明这条路径会把 exact command overhead 重复放大。

## 7.5 不要把 Sequential queue 无限加深

Interactive stepping 是低延迟交互，不是吞吐 benchmark。

目标是：

```text
稳定低延迟 + 有界前压
```

而不是：

```text
decode 尽可能多帧然后排队等用户看
```

# 8. 建议的代码修改范围

## 8.1 `src/application/src/PlaybackCoordinator.cpp`

主要修改点：

### A. 新增 `InteractiveStepRun`

放在 `PlaybackRun` 附近。

### B. 新增 helper

建议至少：

```cpp
bool canUseInteractiveForwardStep(const StepFramesCommand&) const;
void beginInteractiveForwardStep(const StepFramesCommand&);
void enqueueInteractiveForwardStep(const StepFramesCommand&);
bool submitInteractiveStepFrame(...);
void prepareInteractiveStepSuccessor();
void publishInteractiveStepFrameIfReady();
void commitInteractiveStepFrameIfComplete();
bool handleInteractiveStepTerminal(const RequestTerminal&);
void stopInteractiveStepRun(CancellationReason);
void invalidateInteractiveStepContinuity();
```

### C. `beginStep()`

从：

```cpp
beginSeek(command.context, target);
```

改成：

```cpp
if (command.delta == 1) {
    enqueueInteractiveForwardStep(command);
    return;
}

beginSeek(command.context, target);
```

### D. command arbitration

当前所有 navigation 都会：

```cpp
supersedePendingSeek()
```

v1.5 必须区分：

```text
forward +1 compatible with active interactive step run
    → enqueue

everything else
    → stop interactive run
    → existing exact navigation path
```

### E. generation policy

当前：

```text
每一个 step → generation++
```

v1.5：

```text
stream start/discontinuity → generation++
stream 中每一帧       → generation 不变
```

这是性能收益最大的控制面改动之一。

# 9. `MultiSourceFrameProvider` 修改原则

理想情况下 v1.5 不需要改变 Provider contract。

继续使用：

```cpp
FrameRequestPriority::Sequential
```

当前已有：

```cpp
kSequentialRequestSlots = 2
readAheadCount = 3
```

先保持不变。

只建议增加诊断统计，便于性能 gate：

```cpp
struct FrameProviderStatistics {
    ...
    uint64_t exactFrameRequests;
    uint64_t sequentialFrameRequests;
    uint64_t sequentialContinuations;
    uint64_t sequentialFallbackExact;
    uint64_t supersededActiveRequests;
};
```

这样 v1.5 能证明优化来自正确机制，而不是偶然 benchmark 波动。

---

# 10. `SourceDecodeActor` / `SoftwareDecoder` 修改原则

**第一阶段不要改 decoder 算法。**

已有：

```cpp
decodeExact()
decodeSequential()
exactSeekCount()
```

已经足够。

建议只增加：

```cpp
sequentialDecodeCount
decoderReopenCount
interruptCount
```

测试长按 300 帧时应看到：

```text
sequentialDecodeCount ≫ exactSeekCount
decoderReopenCount ≈ 0
interruptCount ≈ 0
```

如果这几个指标仍高，再进入 decoder 内部优化。

# 11. UI 侧修改

## 11.1 `ReviewShortcuts.qml`

第一版 **无需修改快捷键结构**。

继续让：

```qml
onActivated: reviewActions.nextFrame()
```

由 OS auto-repeat 驱动。

后端 stream 会把 repeat 从“取消信号”转换成“有界 forward demand”。

这比引入 `Keys.onPressed/onReleased` 更稳定，也不会破坏 `Qt.ApplicationShortcut` 的全局快捷键体验。

## 11.2 `ReviewActions.qml`

无需区分 click/hold。

## 11.3 `ReviewController`

`dispatchNavigation()` 可以继续接受在前一个 navigation 未完成时提交新的 `+1`。

但需要确保：

- terminal Busy/Canceled 不会错误 fail-close；
- `framePending` 在 stream drain 前保持正确；
- `canNext` 根据最后 queued target 而不是只根据 displayedFrame 边界。

最后一点非常重要。

例如：

```text
displayed = lastFrame - 2
requested = lastFrame
```

此时不能继续接受 +1，否则会反复提交 boundary command。

建议 Capability 投影使用：

```cpp
const FrameId navigationBase =
    snapshot_->requestedFrame.value_or(snapshot_->displayedFrame);
```

判断 `canNext`。

# 12. 单视频专项优化

这次用户痛点是 1-source。

但不建议新增完全独立的 single-source decoder pipeline。

原因：

- 现有 `MultiSourceFrameProvider` 已经支持 1 source；
- 1-source 时 FrameSet atomicity 成本非常低；
- 重新建立单独 pipeline 会制造两套 cancellation/state 语义。

v1.5 应先让通用 Sequential path 正确工作。

如果完成后 1-source 仍达不到目标，再做第二阶段：

1. 减少 1-source `FrameSetAssembler` 临时对象；
2. 缩减 map/alignment 查找；
3. direct cache hit → GPU transfer；
4. single-source prepared FrameSet fast path。

这些属于微优化，不是当前 P0 根因。

# 13. UI/状态发布降噪

当前 Exact step 每个 repeat 会伴随大量：

```text
Seeking snapshot
Canceled terminal
new Seeking snapshot
frame ready
presentation ack
Paused snapshot
command terminal
```

v1.5 forward stream 至少应消除：

```text
Canceled terminal storm
generation change storm
repeated exact-seeking resets
```

可进一步采用已有 playback 的思路：

```cpp
kPlaybackProjectionInterval = 33ms
```

对中间 frame metadata projection 做节流。

注意：

- renderer presentation 不节流；
- FrameSet ACK 不节流；
- 只节流 QML 状态镜像；
- stream drain / error / boundary 必须立即 publish。

目标是让 60/120fps 的视觉呈现不被 QML property update 反向干扰。

# 14. 失败与取消语义

## 14.1 Decode failure

- 停止 interactive stream；
- 保留最后一个完整 presented frame；
- cancel current/prepared request；
- generation++；
- publish recoverable error；
- 所有尚未对应呈现帧的 commands 完成 Failed/Canceled。

## 14.2 用户突然反向

例如：

```text
正在 100 → 101 → 102
用户按 Previous
```

规则：

1. 停止 forward stream；
2. cancel 未发布 current/prepared；
3. generation++；
4. 从最后 **已呈现** FrameId 执行 Exact `-1`；
5. 不从 speculative target 计算反向位置。

## 14.3 用户拖 timeline

同上：

```text
stop stream
invalidate generation
exact seek to released timeline target
```

## 14.4 Device loss

复用现有 generation/device identity fail-closed 规则。

# 15. 性能验收标准

仅看 `seek_p95` 不足以证明长按体验改善。

v1.5 必须新增 **hold-next / adjacent-forward-stream gate**。

## 15.1 Fixture

至少：

- 1080p24 H.264 long-GOP；
- 1080p60 H.264；
- 1080p60 HEVC；
- 1080p120 H.264；
- MPEG-4 Part 2；
- 1-source 为 P0；
- 2-source 作为回归；
- 3-source 作为原子性回归。

## 15.2 测试动作

从稳定的中间帧开始：

```text
连续提交 300 次 StepFrames(+1)
```

模拟真实 keyboard repeat：

- 初始 repeat delay；
- 25–35 Hz input pulse；
- occasional 10–20 ms jitter。

另外增加“最大吞吐”模式：

```text
只要 forward lookahead 未满就持续提交 +1
```

验证 pipeline 上限。

## 15.3 必须记录

```text
presented frame IDs
presentation timestamps
FrameSetReady latency
Presentation ACK latency
exactSeekCount delta
sequentialDecodeCount
decoder reopen count
provider cancellation count
generation increment count
cache hit count
frame budget peak
GUI event latency
```

## 15.4 v1.5 P0 门禁

### 正确性

- 300 帧 forward hold：**0 个 FrameId 缺失**；
- presented IDs 严格 `N, N+1, ...`；
- 0 partial FrameSet；
- 0 stale-generation commit；
- release/输入停止后没有长尾队列；
- memory ≤ existing budget；
- shutdown 仍满足现有有界要求。

### 机制

以 300 帧连续 forward step 为例：

```text
playbackGeneration 增量 <= 2
active provider supersede/cancel <= 2
exactSeekCount 增量 <= 2
sequential continuation >= 95%
decoder reopen count == 0   （正常无故障样本）
```

不要接受：

```text
“看起来快了，但 exactSeekCount 还是 200+”
```

这种结果说明根因没有真正消失。

### 体验

1080p60 / 支持的 D3D11VA runner：

```text
warm forward step presentation-gap P50 <= 18 ms
warm forward step presentation-gap P95 <= 25 ms
warm forward step presentation-gap P99 <= 40 ms
first visible response <= 100 ms
```

如果硬件差异太大，则再加一条相对门禁：

```text
v1.5 hold-next P95
    <= v1.4.5 baseline P95 * 0.40
```

即至少降低 60%。

建议把目标定为：

> **相邻 forward hold 的 P95 延迟降低 60–80%，同时 exact seek 数量下降两个数量级。**

# 19. v1.5 最重要的工程原则

**把“连续逐帧”和“随机定位”分开。**

随机定位的优化目标是：

> 快速得到一个精确目标帧。

连续逐帧的优化目标是：

> 保留 decoder continuity，以稳定 cadence 精确呈现每一个后继帧。

当前项目把两者统一走 Exact Seek，是长按顿挫的根本设计冲突。

v1.5 不需要推翻现有媒体架构。现有 `Sequential`、`decodeSequential()`、read-ahead、prepared frame、FrameSet atomicity 和 Presentation ACK 已经构成完整基础。

真正需要做的是：

> **让 forward Step 使用正确的调度语义。**

这应该是 1.5 的核心改动。
